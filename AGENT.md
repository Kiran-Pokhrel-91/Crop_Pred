# AGENT.md - Nepal Crop Prediction Platform

This file is the source of truth for architecture, boundaries, and working rules.
Read it before changing code. If a change conflicts with these rules, update this
document first and explain why.

## 1. Project goal

Build a reproducible geospatial machine-learning platform that predicts crop
yield (and related crop indicators) for Nepal at a configurable grid resolution.
Satellite, climate, terrain, and land-cover features are generated by an offline
Python pipeline; a Django REST API serves predictions; a React dashboard
visualises results and prediction history.

## 2. Non-negotiable boundaries

1. **The ML pipeline is independent of Django.** Nothing under `ml_pipeline/`
   may import Django or anything from `backend/`.
2. **Inference is standalone.** `ml_pipeline/prediction/predictor.py` must be
   usable from a script, notebook, or API. It accepts plain data structures and
   returns plain data structures.
3. **The API stays thin.** Django views validate requests, call services/predictor,
   and serialise responses. No feature engineering or model logic in views.
4. **One configuration entry point.** Environment variables and repository paths
   are resolved in `ml_pipeline/config.py` (ML side) and `backend/config/settings.py`
   (Django side). No hard-coded credentials, absolute paths, or magic numbers in
   pipeline scripts.
5. **Secrets never enter Git.** `.env`, service-account JSON keys, and exported
   credentials are ignored. Commit only `.env.example` with placeholders.
6. **Data and model binaries never enter Git.** `data/**` and `models/**` are
   ignored except for `.gitkeep`. Datasets and artifacts are regenerated or
   stored in external/object storage.
7. **Reproducibility first.** Every dataset row is traceable to a grid ID, a
   time window, and a feature-set version. Training uses a fixed seed, pinned
   requirements, and versioned artifacts.
8. **No notebooks in production paths.** Notebooks may explore, but logic that
   ships must live in importable modules with docstrings.

## 3. Repository layout and ownership

```text
data/            Local data lake: raw -> processed -> final. Git-ignored contents.
models/          Trained artifacts (joblib/JSON/ONNX). Git-ignored contents.
ml_pipeline/     Offline data collection, processing, training, inference.
backend/         Django + DRF API.
frontend/        React + Vite + Tailwind dashboard.
```

- `ml_pipeline/data_collection/` - one script per source, numbered in execution
  order. Scripts are idempotent and CLI-driven.
- `ml_pipeline/utils/` - shared Earth Engine and geospatial helpers only. No
  dataset-specific business rules.
- `ml_pipeline/processing/` - joins, QA, and feature engineering. Must produce
  a single model-ready table keyed by `grid_id`.
- `ml_pipeline/training/` - training, validation, evaluation, artifact writing.
- `ml_pipeline/prediction/` - loading artifacts and serving predictions.
- `backend/apps/satellite/` - grid and satellite feature endpoints.
- `backend/apps/crops/` - crop catalogue and seasonal metadata endpoints.
- `backend/apps/predictions/` - `POST /api/predict/` and prediction history.
- `frontend/src/pages/` - route-level screens; reusable UI in `components/`.

## 4. Data conventions

- **Storage CRS:** EPSG:4326 (WGS 84) for vectors and API output.
- **Metric operations CRS:** a projected CRS configured in `config.py`
  (default UTM zone 45N, EPSG:32645) for distances, areas, and grids.
- **Grid contract:** one row per cell with at minimum
  `grid_id`, `lon`, `lat`, `geometry`; stable IDs across pipeline runs.
- **Time convention:** ISO dates; document the aggregation window per feature
  (for example, monthly composites or a crop-season window).
- **File formats:** GeoParquet for feature tables, GeoJSON only for small
  visualisation payloads, COG/GeoTIFF for rasters.
- **Naming:** snake_case for files, columns, and functions; scripts keep their
  numeric prefix (`01_...`) even though they are executed, not imported.
- **Missing data:** record coverage/QA flags; never silently impute without a
  documented strategy.
- **Leakage:** splits are made by geography or time (or both), never randomly
  across neighbouring cells when spatial autocorrelation is a concern.

## 5. Development phases (build in order)

| Phase | Scope | Exit criterion |
| --- | --- | --- |
| 0 | Repository scaffold, config, environment template | Imports and docs are in place |
| 1 | `01_generate_grid.py`: national grid | Versioned grid file + metadata |
| 2 | Sentinel-2, Sentinel-1, ERA5, terrain, land cover extraction | Per-source CSV/Parquet tables |
| 3 | Historical ground truth + merge + feature engineering | Model-ready table keyed by `grid_id` |
| 4 | Training + evaluation | Versioned best model + metrics report |
| 5 | Standalone predictor | Reproducible predictions outside Django |
| 6 | Django API + database models | Documented, tested endpoints |
| 7 | React dashboard + map | End-to-end prediction flow in the UI |

Do not start a later phase by hard-coding outputs that an earlier phase should
produce. Add a stub and a TODO when a dependency is not ready.

## 6. Coding standards

- Python 3.11+, type hints on public functions, module and function docstrings.
- Use `pathlib.Path`, `logging` (no `print` in library code), and explicit
  exceptions. Never swallow errors with bare `except:`.
- Scripts expose `argparse` CLI options and a `main()` guard.
- Keep functions small and pure where practical; pass configuration explicitly.
- Frontend: functional components, hooks, one API client in `src/api/client.js`;
  no direct `fetch`/`axios` calls scattered through components.
- Formatting: Black-compatible Python, Prettier defaults for JS/JSX.
- Tests: `pytest` for pipeline utilities, Django `TestCase`/`pytest-django` for
  API behaviour. Every bug fix gets a regression test.

## 7. Commands

```bash
# ML environment
python -m venv .venv && source .venv/bin/activate
pip install -r ml_pipeline/requirements.txt

# Backend environment (uv)
uv sync --project backend

# Pipeline (run from repository root)
python ml_pipeline/data_collection/01_generate_grid.py
python ml_pipeline/data_collection/02_extract_sentinel2.py
python ml_pipeline/data_collection/03_extract_sentinel1.py
python ml_pipeline/data_collection/04_extract_era5.py
python ml_pipeline/data_collection/08_extract_and_merge_historical.py
python ml_pipeline/training/train_models.py
python ml_pipeline/training/evaluate.py

# Backend
uv run --project backend backend/manage.py runserver

# Frontend
cd frontend && npm install && npm run dev
```

## 8. Definition of done

- The change respects module boundaries and reads configuration from the
  documented entry point.
- Inputs, outputs, assumptions, and failure modes are documented in the module
  docstring or README.
- No secrets, raw data, or model binaries are staged.
- Relevant tests pass and at least one smoke command was run.
- `README.md` or this file is updated when architecture or workflow changes.
